Questions the doc doesn't settle yet, as of 2026-10-30. Language questions belong to the doc's author, @iko: the plan says they go "as comments on the doc, on the words they're about", and a change to the language is "agreed first and recorded in Decisions". When one is settled, record it there, change the code if needed, and remove it here.

## Questions milestone 2 raises

Found while writing [prompts/milestone-2.md](prompts/milestone-2.md) and checking it against the doc's examples. The type checker needs an answer to each. @iko settled most of question 4 on 2026-10-30; the others haven't been put to @iko yet.

1. **How the prelude declares natives.** The overview's Prelude section says the prelude is "written in Jibb and vendored as `/lib/jibb/prelude`", and that "Only the prelude declares natives, Jibb's jets, and private helpers". The Core language tab gives each native "a Jibb type, a Hoon gate in `/lib/jibb` … and a JavaScript function in the runtime". The Grammar has no syntax for declaring a native, so how does the prelude say that `add` is a native of type `$-([@ @] @)`? The rules of 2026-10-30 make it sharper: outside a `+$` each bare `@` is its own aura variable, and a capital becomes an aura variable only by meeting an atom in a body, which a native doesn't have. So the declaration needs some way to say that `add`'s three atoms share one aura.
2. **How the prelude marks its private names.** Modules: "Everything is exported and read through the import's face, as `card.card`. Only the prelude has private names." The Grammar has no syntax for privacy either.
3. **What the prelude holds, and how much of it milestone 2 writes.** The Prelude table names groups and examples, "such as `(get.by m k)`", and for the data molds says "and the rest", so which names and types make up the prelude? Its list probably belongs in the doc. The plan's milestone 2 builds "the prelude's types", while the Decisions tab's Build order puts "the core prelude gates" in the same step. And which list gates are natives depends on the plan's first open question, "natives that take gates". The prelude must name every union its elements and attributes take, such as spaces, roles and tones; no module may use those names, since no name may shadow the prelude's.
4. **A capital in a local `++`.** @iko settled the rest of this question on 2026-10-30, in the Grammar's Molds and Literals by context and the Decisions rows Inference, Type variables and Text: outside a `+$` each bare `@` is its own aura variable, generalized per `++` if nothing fixes it; a capital that meets an atom becomes an aura variable, and nothing more specific; a number takes `@ud` only if its `++` isn't generic over its aura; and printing an atom whose aura its `++` is generic over is an error. Still open: is a capital in a local `++` the enclosing `++`'s, so that a local helper can name its parent's types, or a fresh one? The proposed reading is the enclosing one's.
5. **Cells of no items or one.** The parser takes `[]` and `[a]` as tuples, as the EBNF's `"[" { item } "]"` allows, and leaves them to the checker. The Literals section may already answer it: "Every literal reads exactly as Hoon reads it", and its table lists Cell. Hoon reads `[a]` as `a` and rejects `[]`. The proposed reading is Hoon's. Whatever the answer, the theme's `dark=[tones=[…]]`, a record of one field, must still check.
6. **A change with no items.** `m()` parses as a change with no edits, as `wing "(" { item } ")"` allows. Is it an error?
7. **The doc's blocks that aren't whole modules.** The plan's "Done when" for milestone 2 says "the doc's examples typecheck, except those written as errors". Three `jibb` blocks need context to check. The overview's `cmd` and `sub` molds (`doc-overview-01-cmd-sub`) are what the Effects decision calls "the library unions", so in a module of their own they would shadow the prelude's. The Core language tab's `update` (`doc-core-02-update`) is a part of the todo list island. And the Grammar's imports (`doc-grammar-01-imports`) import `/sur/todo.hoon` and `/ui/components/card`, which the doc doesn't show, and the `%todo-action` mark, which the overview shows but which imports `/sur/todo.hoon` itself. The proposed reading is to check each in its context: the first as prelude source, the second inside the island, the third against fixture files.
8. **Tuples and records.** Molds: "Faces are part of the type, so `[a=@ b=@]` and `[x=@ y=@]` don't unify", and a cell literal "takes a default when its `++` is checked", a tuple. Can a tuple meet a record? The doc's examples need it to: worked example 3's `init` gives `[ts "" ~]` for the `model` record, and the basket's `init` gives `[[~ %.n] ""]`; `row-of` gives `[id.t …]` where `each` takes `[key=* el=(element M)]`; `|=%typed` builds `[%typed t]` for the case `[%typed text=@t]`, which the Grammar calls "a case `[%typed @t]`"; and `program` and `store` can't know the faces of samples such as `[=msg m=model]` and `[a=cart-action s=state]`. The proposed reading: a position without a face unifies with one that has a face, and takes it; two different faces don't unify.
9. **Values where `*` is expected.** Molds: "**Any noun**: `*`", with "no subtyping". `each` and `table` take `key=*`, and worked example 3 passes a `@ud` key. How does a typed value meet `*`? One reading: `*` in a gate's mold is a fresh type variable, so any value fits, and the rule against gates in keys comes from the core-language proposal.
10. **What `link`, `image` and `go` take.** Links and URLs: "`link`, `image` and `go` also take two kinds of unchecked cord", besides application paths, and `image`'s `src` is "an application path to a static image or `[url=@t width=@ud height=@ud]`". But the Effects block has `[%go url=@t]`, and a union of a `qath` and a cord breaks the union rule, since "molds that can be either … overlap both" and the Core language tab lowers an application path to "A list of knots". `link` is in worked example 1. Two gates, or a type-directed rule listed in the Grammar ("No built-ins; type-directed rules are welcome, each listed in the Grammar tab")?
11. **Stores and derived gates.** "`poke` and `paths` are declarations, not molds" in an API file; is a store's `+$ poke` one too, since as a mold it would shadow the prelude's opaque `poke`? How does the checker know a module is a store before it has checked `main`, whose type decides the kind? What may a derived name clash with, given that the doc's API file imports `/-  todo` and has a `%todo` case whose request is `todo`? And since "islands can't watch paths that need a separate scry path", is watching a request whose case has `scry=` a type error?
12. **How to print a union without a name.** Jibb has no syntax for one, but Hoon imports bring them in, as in a field's `?(%approve %deny)`, `$@` and `$^`, and the fold of a `(facts full d1 d2)` request does too. How should messages and `types.txt` print them? @iko's decision calls for "a print-only notation".

## Grammar questions never put to the doc's author

In milestone 1 the parser met about thirty places where the doc could be read more than one way. Twelve went to @iko on 2026-10-30 and are rows of the Decisions tab. These were not asked. For each, the parser follows the reading below, and some are marked "(doc question)" in the library's notes. None changes what a valid program means, except where a reading makes something an error.

| # | Question | What the parser does now |
| --- | --- | --- |
| 1 | `knot` may be empty, so the EBNF admits `//`, `/a//b` and a trailing `/`. Which are paths? | A segment has at least one character, as in Hoon. `/` alone is the empty path, in expressions and molds; `%/` alone is the root application path. `//` fails at the second `/`, and a trailing `/` just past it. `inline-mold-paths` has `/` alone as a mold |
| 2 | Is `/` alone a valid path for a `/=` import? | No: `/=` names a module's file, so its path has a segment. `/=  card  /` fails just past the `/` (`inline-import-root-bad`) |
| 3 | The EBNF's `line = [ name "=" ] expr` lets every open bracket's lines take `name=`. What would it mean on a line of an open `(` or `~[`? | An error: `name=` lines belong to tuples and changes. "expected a space between items, found `=`; `name=value` goes in a cell, as [a=1], or a change, as m(a=1)" |
| 4 | Does "items named" make every item of a change need `name=`? | Yes: `m(x)` fails just past `x`, "a change's items are named, as in m(done=%.y)" (`lex-tight-change-bad-3` to `-7`; `-8` and `-9` test what follows a name there). `m()` parses; see question 6 above |
| 5 | `term` includes `%0`, `%&` and `%\|`, which no mark is called. What does `/%` take? | `%` and a name only: `/%  %0` is "expected a mark's term, as `%todo-action`, found `%0`" |
| 6 | What does an indented first line mean? | An error: "the first line is indented: top-level lines start at column 1" (`lex-indent-bad-3`) |
| 7 | With levels open at columns 1 and 5, what does a line at column 3 mean? | An error naming the open columns: "this line's indentation matches no enclosing line: indent it to column 1 or 5". `lex-indent-bad-2`, with levels at 1, 5 and 7, gives "column 1, 5 or 7" |
| 8 | Tabs, carriage returns, other control characters, and non-ASCII text outside strings and comments? | Errors everywhere, strings and comments included, except that UTF-8 is allowed in strings and comments; a tab in a string is written `\09`. `lex-indent-bad-1` and `lex-spacing-bad-2` test tabs |
| 9 | Must a file be valid UTF-8? | Not checked yet: any byte from 128 up passes in strings and comments, and columns assume UTF-8. The proposed reading makes a byte that can't continue a UTF-8 sequence an error. An escape such as `\ff` still writes any byte, as in Hoon |
| 10 | Inside `{…}`, may `::` start a comment, which would swallow the `}` and the `"`? Is a lone `}` in a string text? May a comment follow code with no space, as in `5::note`? | A `:` inside `{…}` is "a comment can't start inside `{…}`". A lone `}` is text, as in Hoon. `5::note` is `5` and a comment |
| 11 | Is a type variable exactly one capital letter, as `typevar = upper` says? | Yes: `Msg` is "a type variable is one capital letter" |
| 12 | Hoon has more runes of the left-out kinds than the list names: `?~ ?= ?. ?@ ?^`, `:- :+ :^ :_`, `%- %+ %^ %~`, `=+ =? =.`, `;:` and `~&(…)`. Are they all left out? | Yes, with the list's reasons, as "`:-` is left out: indentation covers it; write a cell as [a b]". Naming them in the doc, or saying "Hoon's other runes", would make the messages the doc's words (`inline-leftout-*`) |
| 13 | `@s…` and `@r…` auras are "errors wherever used". Is that the parser's error in Jibb source, or the checker's? | An error before the checker. Where a mold goes, the layout pass's, at the `s` or `r`: "signed and floating-point auras are left out of Jibb". Where an expression goes, the parser's, at the `@`: "expected an expression, found `@`; signed and floating-point auras are left out of Jibb". Imported ones are milestone 2's importer's. The case `inline-leftout-signed-float-auras` still says "expect: unclear" |

Where an error points is not a doc question: the doc asks only for "errors with file, line, column and an excerpt". The library puts each error at the first character where the text stops being the start of any valid module, as Hoon's parser does (its section 2.0).
